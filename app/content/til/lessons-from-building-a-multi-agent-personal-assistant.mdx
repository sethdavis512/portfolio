Sprocket is my personal assistant. It manages contacts, tasks, events, journal entries, habits, shareable pages, polls, and booking links, drafts emails, and runs weekly reviews. I wrote the first version of this post when it was a supervisor delegating to more than a dozen specialists, and I argued that layout was the way to build this kind of app.

Then I deleted eleven of those specialists. This is the updated version.

## What I got wrong

The original pitch for specialists sounded right: each one loads only the prompts and tools for its domain, so context stays small and a tool call reads like a story ("RelationshipManager logged a call with Alex").

In practice, most of my specialists only wrapped a set of tools. Contacts, tasks, calendar, habits, research, and the rest each sat between the supervisor and a handful of database calls. Logging a call meant the supervisor picking a specialist, the specialist picking a tool, and two models doing work that one could do. It also meant a 19-line list of routing rules in the supervisor's prompt, just to keep it pointed at the right specialist.

So I flattened it. The eleven wrappers went away and their tools moved onto the supervisor, with a one-line note per domain in its instructions. That commit removed about 600 lines net.

## What the structure looks like now

```
Sprocket (supervisor, ~70 tools)
├── input processor (injects the current date and time)
└── delegates only to:
    ├── JournalCoach    (reflective conversations, writing entries)
    ├── WeeklyReviewer  (gathers a week of data, writes the digest)
    └── EmailDrafter    (pulls contact context, writes the draft)
```

## When a sub-agent earns its place

The three that survived have something in common: they gather first, then synthesize. WeeklyReviewer pulls a week of data across domains and turns it into a digest. EmailDrafter looks up the recipient's history before writing a line. JournalCoach reads past entries and holds a reflective conversation.

That gives me a simple test, which now lives in the repo's docs as a rule: a single-tool domain doesn't get a sub-agent. If the job is "call the right tool," the supervisor does it. If the job is several steps of reading followed by writing, it can be worth a sub-agent.

## A big tool list needs a capable model

Moving every tool onto one agent changed what the model had to do. Choosing among 70 tools on every turn is a harder job than routing to a short list of specialists. Haiku invented tools and narrated its delegations under that load. Sonnet picks the right one in a single step, so the supervisor and all three sub-agents now run on Sonnet.

Tool design helped as much as the model did. I merged tools that overlapped: separate list and search tools became one `find_<domain>` with optional filters, publish and unpublish became `set_<thing>_published`, and four `add_*_to_page` tools became one `add_page_blocks`. That took the count from 80 to 67.

## Cut the domains you don't use

The assistant used to list money and GitHub among the things it could do, because its instructions named them as domains. I detached those nine tools and dropped both domains from the instructions. What the instructions name is what the assistant offers, so trimming them trims the product.

## The model layer is the real product

Every tool calls into a typed data layer (`app/models/*.server.ts`), the same data the app's screens show. Anything the agent creates shows up at `/tasks` or `/events`, where I can check and edit it by hand.

That boundary has paid off twice:

- **Swapping the agent framework.** I moved Sprocket from VoltAgent to Mastra, and the change stayed in the agent layer: tools, memory, and stream handling. The data they read and write didn't care. Old conversations came along too, because a thread the new memory has never seen is seeded from my own copy in the database.
- **Opening it to other clients.** An MCP server at `/api/mcp` exposes the supervisor's tools to Claude Code and other MCP clients. A task I create from a coding session shows up at `/tasks`, the same as one I create in Sprocket's chat.

Public surfaces fall out of the same data. A published event at `/public/events/<slug>`, a shareable page at `/public/pages/<slug>`, and a booking link at `/book/<slug>` are all things the agent can set up, and those public routes read the same data.

## The small things around the model

**The current date and time.** An input processor adds them to every request. Models are bad at temporal reasoning if you don't tell them what "today" is, so this is a few lines of code with an outsized payoff.

**Working memory.** A small schema, validated with Zod, holds my name, preferences, and recurring topics. It's scoped to me rather than to a thread, so the assistant remembers across conversations.

**Confirmation in the UI.** Delete tools never delete anything. They return a preview and the interface asks me to confirm, so the model can't talk itself into a destructive action, and it doesn't need to ask permission in prose.

**Cards for results.** The UI renders a card for every tool result, and the instructions tell the model not to repeat that data in text. That keeps responses short.

## What I'd tell myself at the start

Start with one agent and well-designed tools. Add a sub-agent when a job clearly needs its own gather-then-write loop, and not because a domain feels like it deserves a name. Put the effort into the data layer and the tools, since those outlasted my agent layout and my agent framework.
